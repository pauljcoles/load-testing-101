The Hole

You have a pile of blocks (requests) and a hole to push them through (your pods and load balancer). Three questions: how big is the hole, how many blocks fit through at once, and how long until they are all through.

The answers

All of this comes from Little's Law: the number of requests in the system equals the arrival rate times the time each one spends there (L = λ × W). Turned round, throughput = concurrency ÷ response time. That is why a pod handling 1 request at a time, at 120 ms each, passes about 8 requests a second.

How the numbers are worked out
  • One pod passes this many a secondblocks at once × 1000 ÷ ms in the hole
  • Size of the holepods × per pod, capped by the load balancer
  • Time to get them all throughtotal blocks ÷ the slower of arriving and hole size
  • Blocks inside the system at any momentarriving per sec × ms ÷ 1000
  • Pods you needarriving ÷ (per pod × safe level), rounded up

Why the front end cares

When the hole fills up, requests wait in the queue, so every response gets slower. The user sees that as a slow page: later first paint, later Largest Contentful Paint, buttons that lag. Backend numbers alone (requests per second, p95 latency) do not show how bad that feels, so measure both at the same time.

k6 does this directly. Its browser module drives a real Chromium and reports web vitals, and you can run it as one scenario alongside a normal protocol-level load scenario in the same test. Set a threshold on LCP and see it degrade as the load goes up. JMeter only speaks HTTP and does not render pages, so it needs extra pieces such as the WebDriver Sampler plugin to get browser timings, which is more setup and harder to run at scale.
